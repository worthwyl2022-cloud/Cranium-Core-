# Security Policy

## Scope

`Cranium-Core-` is a historical research and evidence repository. Security reports are welcome for repository contents, automation, documentation, and research tooling. The canonical authority kernel is maintained separately in `cranium-kernel`; report kernel-specific issues to that repository as well.

## Reporting a vulnerability

Please do not publish a suspected vulnerability, credential, personal data exposure, or exploit proof of concept in a public issue before maintainers have had an opportunity to assess it. Send a concise private report to the repository maintainer through the GitHub account contact channel. Include:

- Affected file paths, commits, or releases.
- A clear description of the potential impact.
- Safe, minimal reproduction steps when available.
- Any suggested mitigation or redaction needs.

Maintainership will acknowledge reports when practical, assess scope, coordinate remediation, and request disclosure timing if needed. No response-time or bounty commitment is made by this policy.

## Secret handling

- Never commit passwords, API keys, access tokens, private keys, credentials, session data, or unredacted sensitive datasets.
- Keep local secrets in ignored configuration such as `.env`; use `.env.example` only for non-sensitive placeholder names and documentation.
- Revoke and rotate a credential immediately if it is committed or otherwise exposed. Then remove it from active use; deleting a file alone does not invalidate a leaked secret.
- Review generated reports, receipts, logs, and exports for credentials, personal data, internal paths, and unnecessary sensitive content before publishing.

## Repository hygiene

Generated bytecode, local environments, build output, and local configuration are excluded through `.gitignore`. Treat those exclusions as safeguards against accidental commits, not as a guarantee that a secret has never entered repository history.

## Out of scope

This policy does not promise production security certification, service-level commitments, or a security bounty. Historical reports and research artifacts should not be interpreted as current deployment attestations.
